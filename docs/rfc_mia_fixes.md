## Аннотация

Этот RFC описывает критические архитектурные уязвимости, инфраструктурные "бутылочные горлышки" и недоделки в проекте Mia PM OS v1.9, которые приведут к отказу системы в реальных условиях строительного производства. RFC предлагает конкретные решения для устранения каждого недостатка с приоритизацией по степени критичности.

## Проблемы

### 1. Инфраструктурные проблемы

#### 1.1 VRAM коллизия моделей (CRITICAL)

**Проблема**:
- Заявлено использование RTX 5060 16 GB и одновременный запуск двух моделей: Qwen2.5-14B-Instruct и Qwen2.5-Coder-14B-Instruct в Q4_K_M
- Каждая модель весит ~9 GB, с KV-кэшем при контексте 8K занимает 11-12 GB VRAM
- Две модели одновременно в VRAM не поместятся

**Последствия**:
- Жесткий свопинг в RAM (1-2 токена/сек)
- Out of Memory (OOM) краш
- SingleThreadedWorkerPool заблокирован часами

**Решение**:
- Внедрить динамический горячий сплит в `vram_policy.py`: выгружать Instruct-модель при вызове Coder
- Использовать одну базовую модель Qwen2.5-14B-Instruct для обеих задач (кодовые способности достаточны)
- Перейти на более жесткое квантование Q3_K_L или IQ4_NL для удержания модели в 13 GB VRAM

**Приоритет**: P0 (Критический)
**Этап**: 1

#### 1.2 SQLite не справится с нагрузкой (CRITICAL)

**Проблема**:
- SQLite используется для audit_log, llm_task_queue, object_events, system_commands_log
- 108 объектов, парсинг Excel/PDF, параллельный скрапинг Telegram
- SQLite быстро поймает "database is locked"

**Последствия**:
- Потеря алертов
- Зависание Telegram-ботов при записи тяжелых логов
- Утеря данных аудита из Контура 3

**Решение**:
- Перенести транзакционную нагрузку (очереди, логи, события) на PostgreSQL
- SQLite оставить как локальный кэш конфигурации
- Использовать один SQLite файл на один объект для project_ledger_manager

**Приоритет**: P0 (Критический)
**Этап**: 1

### 2. Архитектурные противоречия

#### 2.1 Деградация ChromaDB для Excel/смет (HIGH)

**Проблема**:
- document_ingestor с текстовым чанкингом превратит смету в нечитаемый текстовый мусор
- Векторный поиск потеряет числовые зависимости (стоимость, объем)

**Последствия**:
- LLM будет галлюцинировать на вопросы "Сколько арматуры в спецификации объекта Х?"

**Решение**:
- Заменить текстовый чанкинг для Excel/смет на структурированный парсинг (Markdown Tables или JSON)
- Внедрить гибридный поиск: Векторный (ChromaDB) + Табличный SQL-поиск через метаданные

**Приоритет**: P1 (Высокий)
**Этап**: 2

#### 2.2 Контур 3 без Safe Tool Layer (CRITICAL)

**Проблема**:
- Контур 3 генерирует CodeCandidate и новые кодовые обработчики
- Safe Tool Generation Layer отложен (DEFERRED)
- Генерируемый код имеет прямой доступ к Studio и базе данных

**Последствия**:
- LLM может сгенерировать деструктивный SQL-запрос (DROP TABLE)
- Безвозвратное удаление данных по объектам

**Решение**:
- Немедленно вывести Контур 3 из продакшена до реализации Safe Tool Generation Layer
- Разрешить LLM генерировать только параметры для жестко прописанных функций (интенты)
- Запретить генерацию сырого исполняемого Python/SQL-кода

**Приоритет**: P0 (Критический)
**Этап**: 1

### 3. Критические недоделки (DEFERRED Components)

#### 3.1 Chronological State Replay Engine (HIGH)

**Проблема**:
- Строительный проект динамичен
- RAG может выдать старый чанк сметы (от прошлого месяца)
- Система рассчитает неверный burn rate и Health Score

**Решение**:
- Реализовать версионирование чанков в ChromaDB
- Внедрить обязательный фильтр по метаданным: `{"status": "actual", "timestamp": "latest"}`

**Приоритет**: P1 (Высокий)
**Этап**: 2

#### 3.2 Implicit Override Detection (HIGH)

**Проблема**:
- Инженеры загружают файлы: Смета_правленная_последняя.xlsx, Смета_ИТОГ.xlsx
- Без детекции оверрайдов система учитывает обе сметы одновременно

**Решение**:
- Внедрить в document_classifier.py контур сравнения структуры документов
- Если хэш структуры совпадает на 90%, автоматически помечать старый документ как DEPRECATED

**Приоритет**: P1 (Высокий)
**Этап**: 2

#### 3.3 Safe Tool Generation Layer (CRITICAL)

**Проблема**:
- Полное отсутствие изоляции среды выполнения динамического кода
- LLM может генерировать вредоносный код

**Решение**:
- Использовать паттерн "Песочница": выполнение CodeCandidate в изолированном WASM или docker-контейнере
- Read-only доступ к копии БД
- Строгая валидация сгенерированного кода

**Приоритет**: P0 (Критический)
**Этап**: 1

### 4. Бизнес-логика строительного производства

#### 4.1 Health Score не учитывает реальные кассовые разрывы (HIGH)

**Проблема**:
- Health Score рассчитывается по Silence risk и Constraint risk
- Ключевые риски - кассовые разрывы и задержка поставок материалов
- Нет интеграции с 1С:Бухгалтерия или ERP
- Burn rate считается "в вакууме" по документам из Google Drive

**Последствия**:
- Система покажет "Green", а объект стоит из-за отсутствия цемента
- Информация в неструктурированном чате Telegram не распарсена

**Решение**:
- Сделать temporal_logic.py и health_score_engine.py жестко привязанными к финансовым Ledger-файлам
- Приоритизировать telegram_distiller: вычленять сообщения со словами-маркерами ("стоим", "нет материала", "не приехали", "задержка")
- Автоматически присваивать наивысший вес риска в negative_event_trigger.py

**Приоритет**: P1 (Высокий)
**Этап**: 2

### 5. Технологический долг в структуре кода

#### 5.1 Дублирование модулей (MEDIUM)

**Проблема**:
- alert_dispatcher.py и temporal_logic.py лежат одновременно в app/modules/object_diary/ и app/modules/temporal/
- Явный признак рассинхронизации разработки
- Изменения в одном файле не применятся к другому

**Решение**:
- Удалить дубли из app/modules/temporal/
- Импортировать модули строго из единого пространства (app/modules/object_diary/)

**Приоритет**: P2 (Средний)
**Этап**: 3

#### 5.2 SingleThreadedWorkerPool - узкое горлышко (HIGH)

**Проблема**:
- SingleThreadedWorkerPool для тяжелых задач (парсинг PDF, OCR, RAG-инжест, генерация LLM)
- Если один пользователь отправит PDF-чертеж на 50 страниц, Telegram-бот перестанет отвечать всем

**Решение**:
- Переписать worker_pool.py с использованием Multiprocessing или Celery/Redis
- Выделить под LLM один поток/процесс (из-за VRAM)
- Выделить под парсинг документов пул из 4-8 CPU-процессов

**Приоритет**: P1 (Высокий)
**Этап**: 2

## Метрики успеха

### До исправлений:
- VRAM: 11-12 GB на модель (OOM риск)
- SQLite: database is locked при нагрузке
- RAG: галлюцинации на Excel данных
- Health Score: ложные позитивы
- Worker Pool: блокировка всей системы

### После исправлений:
- VRAM: <13 GB на модель (стабильно)
- PostgreSQL: concurrent запросы без блокировок
- RAG: точные ответы на табличные данные
- Health Score: реальные риски по материалам/финансам
- Worker Pool: параллельная обработка 4-8 задач

## Риски

### Риски реализации:
- PostgreSQL миграция может потребовать downtime
- Multiprocessing Worker Pool потребует Redis
- Версионирование чанков в ChromaDB может увеличить размер БД

### Митигации:
- План миграции с нулевым downtime (read-replica → cutover)
- Redis кластер для отказоустойчивости
- Компрессия старых чанков, архивирование
